what is SQL?

SQL is the language of data

SQL — Structured Query Language — lets you talk to a database. Think of a database as a collection of Excel sheets that are connected to each other, can hold millions of rows, and respond to precise questions instantly. Every company uses one.

key vocabulary

Term Plain-English meaning
table A grid of rows and columns — like one Excel sheet
row / record One entry — e.g. one order
column / field One attribute of every row — e.g. amount, city
query An instruction you write in SQL to retrieve or change data
NULL A missing value — not zero, not empty string, just absent

level 1 — beginner
founder's take

"SELECT is the foundation of everything. 90% of the queries your entire data team runs are SELECT statements. Master reading data before you touch anything else."

SELECT · FROM · AS

Fetch all data

SELECT *
FROM   orders;

-- * means "all columns"
-- Returns all 8 rows, all 7 columns

Real life: A founder opens their dashboard — the app runs this query behind the scenes to populate the orders table on screen.

Fetch specific columns

SELECT customer, product, amount
FROM   orders;

-- Returns only 3 columns for all 8 rows
-- Always name columns — faster, cleaner

Real life: Finance needs only customer names and amounts for an invoice check — not dates or cities.

Rename columns with AS

SELECT
  customer  AS "Customer Name",
  amount    AS "Order Value"
FROM orders;

-- AS renames the column in output only
-- The actual table is unchanged

Real life: Preparing a board-ready report where column headers must be human-readable, not database-code.

Pitfall: SELECT * is fine for exploration but avoid it in production code — it pulls unnecessary data, slows queries, and breaks things when columns are added or removed.

practice

1. Write a query showing only customer, city, and status.

2. Alias amount as "Revenue" in the output.

3. How many unique products can you spot in the table?

level 2 — beginner
founder's take

"WHERE is where business logic lives. Every segment, every filter, every cohort in your analytics — it's all a WHERE clause. Get comfortable writing conditions and you'll be answering business questions in minutes instead of days."

WHERE — filtering rows

Simple filter

SELECT customer, amount
FROM   orders
WHERE  status = 'paid';

-- Returns 5 rows — all paid orders
-- Text values always need single quotes

Real life: Revenue report — show only paid orders, exclude pending and refunded.

Multiple conditions — AND, OR

SELECT customer, city, amount
FROM   orders
WHERE  city = 'Mumbai'
  AND  status = 'paid';

-- Both conditions must be true
-- Result: Priya (12000), Priya (7200), Sneha (11000)

Real life: Mumbai-specific revenue for a regional sales review.

Numeric comparisons and IN

SELECT customer, amount
FROM   orders
WHERE  amount > 10000;

-- Operators: =  !=  >  <  >=  <=

SELECT customer, status
FROM   orders
WHERE  status IN ('paid', 'pending');

-- IN is shorthand for multiple OR conditions

Real life: Flag all active orders (paid + pending) for a pipeline review — exclude refunded.

ORDER BY · LIMIT · DISTINCT

Sort + limit results

SELECT customer, amount
FROM   orders
WHERE  status = 'paid'
ORDER BY amount DESC
LIMIT 3;

-- DESC = highest first · ASC = lowest first
-- LIMIT 3 returns only top 3 rows

Real life: Homepage "Top 3 orders this month" widget on your dashboard.

Remove duplicates with DISTINCT

SELECT DISTINCT city
FROM   orders;

-- Returns: Mumbai, Delhi, Bengaluru
-- Mumbai and Delhi appeared multiple times
-- DISTINCT removes the repeats

Real life: Populating a city filter dropdown in your app — you need unique values only.

Pitfall: LIMIT without ORDER BY returns a random subset. The database picks whichever rows are fastest to retrieve. Always sort before limiting if you care about which rows you get.

practice

1. Find all orders from Delhi with amount greater than 7000.

2. Show the 2 most expensive orders by amount.

3. List all unique products — no duplicates.

4. Find all orders that are NOT paid. (Hint: != 'paid' or NOT IN)

level 3 — intermediate
founder's take

"The moment you learn GROUP BY, you stop answering 'show me the data' and start answering 'what does the data mean'. Every KPI, every weekly metric, every investor update number comes from a GROUP BY query."

aggregate functions

The five core aggregates

SELECT
  COUNT(*)         AS total_orders,
  SUM(amount)      AS total_revenue,
  AVG(amount)      AS avg_order,
  MAX(amount)      AS biggest_order,
  MIN(amount)      AS smallest_order
FROM   orders
WHERE  status = 'paid';

-- Result: 5 | 55700 | 11140 | 15000 | 7200

Real life: The Monday morning revenue Slack message your CEO sends — this one query produces all the numbers in it.

GROUP BY — summaries per group

Revenue per city

SELECT
  city,
  COUNT(*)       AS orders,
  SUM(amount)    AS revenue
FROM   orders
WHERE  status = 'paid'
GROUP BY city
ORDER BY revenue DESC;

-- Mumbai: 3 orders, ₹30200
-- Bengaluru: 2 orders, ₹28000
-- Delhi: 1 order, ₹8500

Real life: Regional performance slide in a board deck — which cities are driving the most revenue.

Revenue per product

SELECT
  product,
  COUNT(*)      AS units_sold,
  SUM(amount)   AS revenue
FROM   orders
GROUP BY product;

-- CRM Pro: 5 orders  (including pending)
-- Analytics: 3 orders

Real life: Which product is actually selling — classic founder question at the end of every month.

HAVING — filter groups, not rows

WHERE vs HAVING — the most common interview trap

-- WHERE filters rows BEFORE grouping
-- HAVING filters groups AFTER grouping

SELECT city, SUM(amount) AS revenue
FROM   orders
GROUP BY city
HAVING SUM(amount) > 15000;

-- Only cities with total revenue above 15000

-- ❌ This causes an error:
-- WHERE SUM(amount) > 15000

Real life: Find customer segments that crossed a spending threshold — trigger a loyalty reward automatically.

SQL execution order — memorise this

1
FROM
2
WHERE
3
GROUP BY
4
HAVING
5
SELECT
6
ORDER BY
7
LIMIT

This order explains why you can't use a SELECT alias in WHERE — SELECT hasn't run yet at that point.

practice

1. Find total revenue per product for paid orders only.

2. Which city has the highest average order amount?

3. Show cities where total paid revenue exceeds ₹20,000 (use HAVING).

4. Count orders by status — how many paid, pending, and refunded?

join types at a glance

INNER JOIN

Only rows that match in both tables. "New Lead" disappears — no orders to match.

LEFT JOIN

All rows from left table, NULLs where right has no match. "New Lead" appears with NULL orders.

RIGHT JOIN

All rows from right table + matching left. Rare — just flip the tables and use LEFT JOIN instead.

FULL OUTER JOIN

All rows from both tables, NULLs filling gaps on either side.

INNER JOIN — link orders to customer plans

SELECT
  o.customer,
  c.plan,
  c.account_manager,
  o.amount,
  o.status
FROM   orders     AS o
INNER JOIN customers AS c
       ON o.customer = c.name;

-- o. and c. = table aliases (use them always)
-- "New Lead" is excluded — no orders

Real life: Which plan tier is generating the most revenue? Enterprise vs Starter vs Pro.

LEFT JOIN — include customers with zero orders

SELECT
  c.name,
  c.plan,
  COUNT(o.id)                    AS orders,
  COALESCE(SUM(o.amount), 0)    AS revenue
FROM      customers AS c
LEFT JOIN orders     AS o
          ON c.name = o.customer
GROUP BY  c.name, c.plan
ORDER BY  revenue DESC;

-- "New Lead" appears with 0 orders and ₹0
-- COALESCE turns NULL into 0

Real life: Customer health check — spot trial accounts that haven't converted yet so sales can follow up.

Pitfall: Adding a WHERE filter on the right-side table after a LEFT JOIN secretly turns it into an INNER JOIN — rows with no match get dropped. Put that filter in the ON clause instead of WHERE.

practice

1. Using INNER JOIN, show each order alongside the customer's account manager.

2. Using LEFT JOIN, find customers who have placed zero orders.

3. What is the total paid revenue per plan tier? Use JOIN + GROUP BY.

level 5 — advanced
founder's take

"Subqueries and UNION separate juniors from seniors. A junior runs three queries and pastes results in a spreadsheet. A senior writes one query and ships the answer in 30 seconds. That's the kind of person I want to hire."

subqueries — queries inside queries

Orders above the average order value

SELECT customer, amount
FROM   orders
WHERE  amount > (
  SELECT AVG(amount)
  FROM   orders
  WHERE  status = 'paid'
);

-- Inner query runs first → returns 11140
-- Outer query: WHERE amount > 11140
-- Result: Ananya 15000, Priya 12000, Ananya 13000

Real life: Flag high-value orders that need a personal thank-you from the founder.

Subquery in FROM — build a summary, then filter it

SELECT city, avg_order
FROM (
  SELECT
    city,
    ROUND(AVG(amount), 0) AS avg_order
  FROM   orders
  WHERE  status = 'paid'
  GROUP BY city
) AS city_summary
WHERE avg_order > 10000;

-- Inner query builds a per-city summary
-- Outer query filters it — must alias the subquery

Real life: Which cities have a high enough average order to justify running a local event?

UNION — stack two result sets

-- UNION removes duplicates (slower)
-- UNION ALL keeps all rows (faster)

SELECT customer, amount, 'high-value' AS flag
FROM   orders
WHERE  amount > 12000

UNION ALL

SELECT customer, amount, 'pending' AS flag
FROM   orders
WHERE  status = 'pending';

-- Combines two logically different lists
-- Both queries must return same column count

Real life: One combined outreach list — high-value paid customers for upsell + pending customers for follow-up.

Pitfall: A subquery inside FROM must always have an alias (e.g. AS city_summary). Forgetting it is a guaranteed syntax error. Also: UNION requires matching column count and compatible types in both queries.

practice

1. Find customers whose total spending exceeds the average total spending across all customers.

2. Using a subquery in FROM, show products with total revenue above ₹25,000.

3. UNION a list of paid orders from Mumbai with paid orders from Bengaluru.

"These aren't textbook exercises. These are the exact queries I've asked analysts to run at 10pm before a board meeting. If you can write these fluently, you are genuinely valuable on day one."

scenario 1 — weekly revenue report

What lands in the CEO's inbox every Monday

SELECT
  city,
  COUNT(*) FILTER (WHERE status='paid')     AS paid,
  COUNT(*) FILTER (WHERE status='pending') AS pending,
  SUM(amount) FILTER (WHERE status='paid')   AS revenue
FROM   orders
GROUP BY city
ORDER BY revenue DESC;

scenario 2 — data quality check

Find customers who placed more than one order

SELECT
  customer,
  COUNT(*) AS order_count
FROM   orders
GROUP BY customer
HAVING COUNT(*) > 1;

-- Priya and Rahul and Ananya each appear twice
-- Useful for spotting duplicates or loyal customers

scenario 3 — customer vs target

How much has each customer spent vs their plan limit?

SELECT
  c.name,
  c.plan,
  COALESCE(SUM(o.amount),0)        AS spent,
  ROUND(100.0 *
    COALESCE(SUM(o.amount),0)
    / CASE c.plan
        WHEN 'Enterprise' THEN 50000
        WHEN 'Pro'        THEN 25000
        ELSE 10000
      END, 1)                        AS utilisation_pct
FROM      customers c
LEFT JOIN orders     o
          ON c.name = o.customer
         AND o.status = 'paid'
GROUP BY  c.name, c.plan;

Real life: Customer success team's monthly health check — who's near their plan limit and ready for an upsell conversation.

conceptual questions

Q1 — CONCEPTUAL

What is the difference between WHERE and HAVING?

WHERE filters individual rows before any grouping happens. HAVING filters groups after GROUP BY runs. You cannot use aggregate functions like COUNT() or SUM() in a WHERE clause — the grouping hasn't happened yet so there is nothing to aggregate. Use WHERE to reduce the rows going in; use HAVING to reduce the groups coming out.

Q2 — CONCEPTUAL

What is the difference between DELETE, TRUNCATE, and DROP?

DELETE removes specific rows — you can add a WHERE clause and roll it back in a transaction. TRUNCATE removes all rows instantly — much faster, but cannot be rolled back in most databases, and the table structure remains. DROP removes the entire table including structure, constraints, and indexes — no recovery without a backup.

Q3 — CONCEPTUAL

What is NULL and how is it different from 0 or an empty string?

NULL means the value is unknown or absent. It is not zero and not an empty string — it is the complete absence of any value. Any comparison with NULL using = or != returns unknown, not true or false. You must use IS NULL or IS NOT NULL. Zero is a valid number. An empty string is a valid string of length zero. NULL is neither.

Q4 — CONCEPTUAL

What is the difference between INNER JOIN and LEFT JOIN?

INNER JOIN returns only rows that have a match in both tables — unmatched rows from either side are excluded. LEFT JOIN returns every row from the left table regardless; for rows with no match in the right table, the right-side columns are filled with NULL. Use LEFT JOIN when you cannot afford to lose rows from your primary table, such as when auditing all customers including those with no orders.

Q5 — CONCEPTUAL

What is the difference between UNION and UNION ALL?

Both combine result sets from two SELECT queries. UNION removes duplicate rows, which requires an extra deduplication step and is slower. UNION ALL keeps all rows including duplicates and is faster. Use UNION when uniqueness matters; use UNION ALL when you know duplicates do not exist or performance matters more.

query-writing questions

Q6 — WRITE A QUERY

Find the second-highest amount in the orders table.

SELECT MAX(amount)
FROM   orders
WHERE  amount < (
  SELECT MAX(amount) FROM orders
);

Bonus: mention DENSE_RANK() as the more robust approach if the interviewer asks for alternatives.

Q7 — WRITE A QUERY

Find customers who have placed more than one order.

SELECT customer, COUNT(*) AS order_count
FROM   orders
GROUP BY customer
HAVING COUNT(*) > 1;
Q8 — WRITE A QUERY

Show total revenue per city, only for cities above ₹15,000 in paid orders.

SELECT city, SUM(amount) AS revenue
FROM   orders
WHERE  status = 'paid'
GROUP BY city
HAVING SUM(amount) > 15000;
Q9 — WRITE A QUERY

List all customers and their total paid revenue — include customers with zero paid orders.

SELECT
  c.name,
  COALESCE(SUM(o.amount), 0) AS paid_revenue
FROM      customers c
LEFT JOIN orders     o
          ON  c.name   = o.customer
         AND  o.status = 'paid'
GROUP BY  c.name
ORDER BY  paid_revenue DESC;

Key point: the status filter goes in the ON clause, not WHERE. Putting it in WHERE would silently convert the LEFT JOIN into an INNER JOIN and drop customers with zero orders.

Q10 — WRITE A QUERY

Find orders where the amount is above the average amount of all paid orders.

SELECT customer, amount, status
FROM   orders
WHERE  amount > (
  SELECT AVG(amount)
  FROM   orders
  WHERE  status = 'paid'
)
ORDER BY amount DESC;

Interview tip from a founder: When writing queries live, narrate your reasoning. Say "I need to group first, then filter groups, so I'll use HAVING not WHERE." The candidate who explains a slightly wrong query with clarity often beats the one who writes the right query in silence. Interviewers hire for thinking, not memorisation.
